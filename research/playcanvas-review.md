# PlayCanvas engine review for CORE

Reviewed 12 September 2026. This is a source and documentation review for planning, not a claim that the new game is implemented or that the upstream test suite was run.

## Recommendation

Use standalone PlayCanvas for the proposed full-window, authored 3D data-center environment, with a restrained orthographic camera and accessible HTML interface above the canvas. Keep the simulation, story progression, decisions, save format, and learning material independent of the renderer. The engine is a strong fit for a facility that visibly changes as the player builds, commissions, and operates it; choosing it will not itself fix unclear objectives, weak narrative, or unrealistic tradeoffs.

Use a stable published engine release rather than the cloned development branch. The reviewed clone is `7b00ca4db4bda4c903f4cc727f39b38b43b76aa3`, dated 2026-09-12, reporting `2.23.0-beta.8`. The official release list identifies [v2.22.2](https://github.com/playcanvas/engine/releases/tag/v2.22.2), released September 11, as current stable. Pin and test the chosen release before implementation; APIs observed on main need verification against that release.

## Runtime and maintenance decisions

The main-branch source explicitly recommends `AppBase` for new work: `Application` registers every component and resource handler, preventing selective tree shaking, and its synchronous constructor cannot create WebGPU itself. See [application.js, lines 68–104](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/src/framework/application.js#L68-L104). A tiny exploratory probe can use `Application`; the proposed implementation should use `AppBase` with only rendering, camera, lighting, input, and required assets registered. Physics is unnecessary for initial grid placement, capacities, power routes, and procurement calculations.

The official [browser requirements](https://developer.playcanvas.com/user-manual/engine/supported-browsers/) require WebGL2. WebGPU can be an optional path; the game should not require it. In the reviewed development source, [createGraphicsDevice, lines 88–122](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/src/platform/graphics/graphics-device-create.js#L88-L122) appends WebGL2 and then a null device as fallbacks. A resolved initialization promise therefore must not be treated as proof of visible rendering. Detect the selected device and present a usable simplified facility view or explicit compatibility state.

Budget performance before asset production: cap device pixel ratio, bake most lighting, instance repeated equipment, limit transparency/shadows, pause hidden-tab animation, and keep chapter assets bounded. Verify on real target phones as well as desktop emulation. The [upstream optimization guidance](https://developer.playcanvas.com/user-manual/optimization/) treats load time, frame stability, power consumption, and memory as separate goals. A cube probe proves only engine initialization, not production performance.

The repo is actively versioned and has CI jobs for builds, package exports, linting, declarations, and unit tests in [ci.yml](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/.github/workflows/ci.yml). I inspected their presence; I did not run or certify upstream CI. The examples browser is itself a substantial React/Vite/Monaco development application; its [package manifest](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/examples/package.json) is a reason to run a small isolated probe instead of adding the entire example stack to CORE.

## Story, strategy, and geopolitics remain game systems

The reviewed engine facilities are rendering and interaction primitives, not a curriculum or geopolitical scenario model. Implement these separately:

1. A chapter director controls opening, mentor interruption, objective reveal, construction, consequence, and debrief. All scenes remain skippable/replayable and readable without audio.
2. A deterministic simulation owns budgets, capacity, demand, construction lead times, interconnection, cooling, water, procurement, staffing, operating cost, and resilience dependencies. Scene entities visualize its state; they never independently calculate truth.
3. Scenario data defines a fictional trigger, exposure, signal, lag, affected dependencies, possible mitigations, and downstream consequences. Do not use an animation state graph as a scenario-planning model.
4. A source registry connects mentor explanations and debriefs to reviewed evidence, dates, geographical applicability and explicit simplifications. Source-supported mechanisms and invented scenario parameters must be visibly distinct.
5. Save/replay records decisions and random seeds; comparing alternatives reruns the same external conditions. Teaching feedback explains mechanisms and tradeoffs rather than rewarding one universal build.

## Comparison with melonJS

PlayCanvas is the preferred fit if the intended visual language is a 3D campus with real depth, equipment closeups/cutaways, authored lighting and camera transitions. melonJS remains credible for an illustrated 2.5D strategy game using Tiled maps, and its fallback coverage may be valuable for broad device reach. Do not dismiss current melonJS as exclusively 2D: its checked-out README and source now include `Camera3d`, glTF/GLB scenes, 3D meshes, WebGPU, WebGL2, and Canvas fallback. Evaluate the exact stable release separately from development main. The other specialist's melonJS review provides the detailed comparison.

Whichever renderer wins, the first approval milestone should be one complete, comprehensible 10–15 minute chapter: player arrival → mentor guidance → visible construction decision → consequence → real-world strategy debrief. That tests the user's actual complaint before expanding to many chapters or investing heavily in assets.

## Local execution resource

The minimal reviewed source is [misc/hello-world.example.mjs](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/examples/src/examples/misc/hello-world.example.mjs). Outside the examples browser, replace its `examples/context` import with the selected device constant, import the installed/pinned engine, and supply the named canvas. It requires no artwork or physics. The README also contains an even smaller synchronous `Application` cube. A published release probe can load `https://cdn.jsdelivr.net/npm/playcanvas@2.22.2/build/playcanvas.js` after verifying the returned file/version, then run equivalent code through the `pc` namespace. The coordinator owns downloading/running/verifying the local probes; no probe execution is claimed by this report.

## License boundary

The engine [MIT license](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/LICENSE#L1-L19) permits reuse with notice retention. Example artwork is not uniformly MIT: the [Spine example license](https://github.com/playcanvas/engine/blob/7b00ca4db4bda4c903f4cc727f39b38b43b76aa3/examples/assets/spine/license.txt#L2-L9) restricts images to noncommercial use, while other examples carry asset-specific CC BY credits. Keep the cloned repo as research material; use self-authored primitives for probes and an asset manifest with explicit licenses for the game.
